# Зовнішні компоненти

Ця конфігурація **не застосовується на занятті 8**. Вона тут як робочий приклад
того, про що йшлося в розділі про зовнішні компоненти, і знадобиться далі.

## Чому окремо від cluster/

Провайдер `helm` налаштовується на кластер, якого на момент планування ще
може не існувати. Якщо тримати його в одній конфігурації з кластером, перший
`plan` падає з помилкою підключення — план намагається звернутися до сервера
API, якого ще немає.

Це не обхідний шлях, а стандартна практика: кластер і його вміст майже завжди
розводять по різних конфігураціях.

## Як застосувати, коли дійде черга

```bash
cd cluster
terraform output cluster_name          # скопіюйте значення

cd ../addons
terraform init
terraform apply -var cluster_name=<значення>
```

## Що можна додати сюди далі

| Компонент | Що дає | Чи потрібна роль IAM |
|---|---|---|
| `metrics-server` | `kubectl top`, автомасштабування подів | ні |
| AWS Load Balancer Controller | справжні ALB/NLB для Ingress і Service | так |
| `external-dns` | записи в Route 53 автоматично | так |
| `cert-manager` | TLS-сертифікати від Let's Encrypt | так, для DNS-01 |
| External Secrets Operator | секрети з Secrets Manager у кластер | так |
| Karpenter | вузли під конкретні поди замість груп | так |

Для компонентів із колонки «так» знадобиться роль, прив'язана до службового
акаунта. Приклад такої прив'язки — у `cluster/eks.tf`, блок `aws-ebs-csi-driver`.

Готова альтернатива, яку варто подивитись перед тим, як писати десять
`helm_release` руками: модуль `terraform-aws-modules/eks-blueprints-addons`.
