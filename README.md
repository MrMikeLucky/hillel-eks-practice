# hillel-eks-practice

Навчальний кластер EKS для блоку «Хмари» курсу DevOps в IT Hillel.
Заняття 8 і далі.

Конфігурація свідомо спрощена для навчання. Кожне спрощення позначено
коментарем у коді з поясненням, як це роблять у продакшні.

---

## Що тут лежить

```
bootstrap/   Одноразове: довіра між HCP Terraform і вашим акаунтом AWS.
             Застосовується локально й лише один раз.

cluster/     Сам кластер: VPC, EKS, група вузлів на spot, доповнення.
             Це те, що ви застосовуєте на занятті 8.

addons/      Приклад встановлення зовнішніх компонентів чартами Helm.
             На занятті 8 НЕ застосовується.
```

---

## Швидкий старт

### 0. Що потрібно мати

- акаунт AWS із доступом до консолі;
- організація в HCP Terraform (безкоштовний план);
- `terraform` 1.9 або новіший, `aws` CLI, `kubectl`.

### 1. Довіра між платформою і AWS

Пропустіть цей крок, якщо ви вже налаштували федерацію на попередніх
заняттях — тоді лише додайте воркспейси з префіксом `hillel-eks`
до шаблону `sub` наявної ролі.

```bash
cd bootstrap
cp terraform.tfvars.example terraform.tfvars   # впишіть свою організацію
terraform init
terraform apply
terraform output role_arn                      # знадобиться на кроці 2
```

### 2. Воркспейс у HCP Terraform

1. Створіть воркспейс типу **CLI-driven** з іменем `hillel-eks-dev`
   і тегом `hillel-eks`.
2. У ньому: **Variables → Environment variables** (саме Environment,
   не Terraform — це найчастіша помилка):

   | Ключ | Значення |
   |---|---|
   | `TFC_AWS_PROVIDER_AUTH` | `true` |
   | `TFC_AWS_RUN_ROLE_ARN` | ARN із кроку 1 |

### 3. Кластер

```bash
cd cluster
# впишіть свою організацію у блок cloud у versions.tf
cp terraform.tfvars.example terraform.tfvars   # впишіть свій prefix
terraform login
terraform init
terraform apply                                # ~15 хвилин
```

### 4. Доступ до кластера

```bash
terraform output kubeconfig_command    # скопіюйте й виконайте
kubectl get nodes
kubectl get pods -n kube-system        # знайдіть тут усі п'ять доповнень
```

## Режим життя кластера

Контрольний рівень коштує **$0.10 за годину ($73 на місяць) незалежно ні від
чого** — навіть із нулем вузлів і нулем подів. Вузли додають ще близько $32.

Тому між заняттями ми опускаємо вузли в нуль, а кластер лишаємо:

```bash
# наприкінці кожного заняття
terraform apply -var node_desired_size=0     # вузли зникають, кластер лишається

# на початку наступного
terraform apply -var node_desired_size=2     # ~3 хвилини, і кластер готовий

# після останнього заняття блоку
terraform destroy                            # тоді вже остаточно
```

Перестворювати кластер цілком щоразу невигідно: контрольний рівень
піднімається 9–12 хвилин, а вузли — три.

### Скільки це коштує

| Позиція | Ставка | На місяць |
|---|---|---|
| Контрольний рівень | $0.10 / год | **$73** |
| Два вузли t3.medium spot | ~$0.015 / год кожен | $22 |
| Диски вузлів (2 × 20 ГБ gp3) | — | $3 |
| Публічні адреси (2) | $0.005 / год кожна | $7 |
| **Цілодобово** | | **~$105** |
| **З вузлами в нулі між заняттями** | | **~$80 за блок** |

## Свідомі спрощення

Усі вони позначені коментарями в коді.

| Спрощення | Чому так | Як у продакшні |
|---|---|---|
| Вузли в публічних підмережах, без NAT | NAT коштує ~$32/міс — половина ціни кластера | Вузли у приватних підмережах, вихід через NAT або ендпоінти VPC |
| Публічний ендпоінт сервера API | Інакше потрібен бастіон або VPN | Приватний ендпоінт плюс бастіон |
| Широкі керовані політики для ролі | Щоб не витрачати заняття на налагодження прав | Права звужують до конкретних дій і ресурсів |
| Один вузловий пул загального призначення | Двох вузлів вистачає для навчання | Кілька пулів під різні типи навантаження, часто Karpenter |

## Пастки, через які витрачають вечір

**Теги підмереж.** `kubernetes.io/role/elb` на публічних підмережах — не
косметика. За ними AWS Load Balancer Controller знаходить, де створювати ELB.
Без тега `Service` типу `LoadBalancer` зависає у `Pending` назавжди, і в
подіях немає нічого зрозумілого.

**Версія Kubernetes.** Кожна версія має 14 місяців стандартної підтримки.
Далі кластер автоматично переходить у розширену за **$0.60 за годину** —
$438 на місяць замість $73. Без попередження, просто за календарем.
Конфігурації в коді страждають найчастіше, бо версія закріплена й ніхто її
не рухає. Перевіряйте раз на півроку.

**Вкладка змінних.** `TFC_AWS_*` — це **Environment variables**, а не
Terraform variables. У другій вкладці вони не працюють, а помилка про це
ніяк не натякає.

**Оператор у політиці довіри.** Зірочки в шаблоні `sub` вимагають
`StringLike`. Зі `StringEquals` вони не працюють, і ви отримаєте
`Not authorized to perform sts:AssumeRoleWithWebIdentity`.

**Один тип машин у spot-групі.** Найчастіша причина, чому вузли не
піднімаються: AWS не знайшов вільної потужності саме цього типу.
Три схожі типи роблять групу практично незламною.

**Провайдер helm у тій самій конфігурації, що й кластер.** План падає, бо
провайдер намагається підключитись до кластера, якого ще немає. Тому
`addons/` — окрема тека.

## Дві площини прав, які плутають

| Хто має доступ **до** кластера | Що дозволено поду **всередині** |
|---|---|
| Access entries: роль IAM → права в кластері | Pod Identity: роль IAM → службовий акаунт |
| Прийшли на заміну ConfigMap `aws-auth` | Старший механізм — IRSA через OIDC |
| Далі всередині працює звичайний RBAC | Под отримує тимчасові креденшели, без ключів |

Механізми різні й не пов'язані між собою, хоча обидва базуються на IAM.
